# Conformance vectors

A conformance vector is a known input with the exact output an implementation of the contract must produce. The
vectors ship inside the package, under `src/iltero_schemas/vectors/`, and are available at run time as
`iltero_schemas.vectors.VECTORS`. A consumer that reproduces every vector of the version it pins is conformant. A
consumer that fails one must fail its build.

## Vector folders

| `assertions/` | Assertions written to exercise the language: truth tables, every comparison, comparisons with `null` (`VEC.IAC.RESOURCE.VEC.THING.OPS_NULL`), nesting, edge-case literals, and the comparison a failure's reason names (`VEC.IAC.RESOURCE.VEC.THING.TRUTH_REASON`: an `all` of an `any` of two comparisons and a `not`). | `compiler/` | For every shipped assertion and every vector assertion: the abstract syntax tree (`.ast.json`, which includes the `change_type`: JSON with keys sorted, two-space indentation, non-ASCII characters escaped and one final newline, the same bytes as a record's `<ID>@<version>.ast.json` file for that assertion), its source digest (`.digest`), the compiled Rego program (`.rego`) and the program's digest (`.rego.digest`). Each document folder (`contexts/`, `events/`, `identities/`, `records/`, `reports/`, `run_statements/`,
`scanner_check_mappings/`, `scanner_check_mapping_descriptors/`, `scanner_observations/`, `served_exceptions/`) has one
`digests.json` at its top. Each key is a document's path from that folder, such as `image/post_verify.json`, the same
string a case's `vector` or `context` uses, and the keys are sorted by Unicode code point. A listing names exactly its folder's
documents: a document not in it is not a vector, and every listed document is shipped. A consumer reads each document
folder's `digests.json` and every `cases.json` it finds, never a fixed list of subfolders, and never keys a document
by its file name alone: `contexts/iac/post_verify.json` and `contexts/image/post_verify.json` share one.

The identity vectors hold no resolved identity, because a resolved identity names a real-format cloud identifier, which
this repository does not publish. So these rules of a resource identities document have no vector: no two entries of
`resolved`, or of `removed`, name the same cloud identity; a resource is resolved or unresolved, never both; only a
resource type verified for its provider's resolver is resolved; every resolved identity belongs to the unit and names
the tool that wrote the state; an identifier names a resource of its stated type. A conformant consumer enforces them
all; the validating model `iltero_schemas.models.iac.resource_identities.ResourceIdentities` is the reference.

A document of a run the tool opened names a state by its [state digest](01-document-formats.md#state-digests), the
digest of the redacted state. The records of `raw_states/iac/cases.json` name the digest of the state they were written
from. The other documents that name a state name the redacted state digest, under the built-in policy, of a captured
state of `raw_states/iac/`, chosen for the form of its digest: `refresh_verified.json` for
`contexts/iac/post_verify.json`, and `apply_create.json` for `contexts/iac/post_deploy.json`,
`identities/resource_identities.json`, the case `state_read_after_the_apply` of `evaluation/cases.json` and the case
`state_not_read_with_its_identities` of `records_invalid/iac/cases.json`. These documents name other resources than
that state holds, such as `aws_db_instance.payments`. A test holds each document to its state
(`test_a_document_not_written_from_a_state_names_the_redacted_state_digest_of_the_state_chosen_for_it`). No document
names the digest of the empty state `{"format_version": "1.0"}`,
`sha256:1da85b5bbb58f51444fc8fbc32886f6ecb7a814497cd494cd451d52c37d1e193`, but the case
`terraform_state_that_is_empty` of `redaction/iac/state_cases.json`, and no state digest in the vectors equals it
(`tests/iac/test_raw_states_vectors.py`).

Every document digest is the SHA-256 of the document's RFC 8785 canonical JSON, written `sha256:<hex>`. The
`iltero_schemas.canonical` module computes it with `digest_of`, and the canonical bytes with `canonical_bytes`.
Each document vector is written as its validating model dumps it: every optional field present, `null` when it has
no value. A consumer whose writer produces that form reproduces the vector's bytes and digest.

An ES256 signature is not a pure function of its input, so `scripts/refresh_vectors.py`, which rewrites the generated
vectors, cannot rebuild a signed one. `scripts/sign_descriptor_vectors.py` signs the sample again: it makes a
throwaway development key (`dev-scanner-check-mapping-vectors`), signs `scanner_check_mappings/iac/served_catalog.json`
with it, checks the descriptor with `check_scanner_check_mapping_descriptor` and verifies the signature with the new
key, and forgets the private key. It then rewrites `signing_keys/development.json` with the key's public half,
`scanner_check_mapping_descriptors/iac/served_catalog.json`, and each `scanner_check_mapping_descriptors_invalid/`
case whose signature is derived from the sample's. Run `scripts/refresh_vectors.py` after it to update the digests.

`scripts/sign_run_statement_vectors.py`, run from the repository's root, signs the run statement vectors again. It
makes two throwaway development keys, `dev-run-statements` and `dev-operator-run-statements`, writes them as the keys of
`signing_keys/run_statements.json`, and forgets the private keys once they have signed. It writes each statement of
`run_statements/` and each case of `run_statements_valid/` and `run_statements_invalid/`, from the case table
`scripts/run_statement_vector_cases.py`, after checking that the package agrees with each case. A statement names its
record's digest, so a record vector that changes needs this script run again
(`test_each_statement_verifies_and_names_its_record_as_the_record_is_now` finds a stale one). Run
`scripts/refresh_vectors.py` after it: the reports name the statements' digests. `scripts/write_trust_vectors.py`
writes the sample operator trust file `signing_keys/operator.json` with a new key whose private half it forgets; no
vector is signed with it.

## The pinned OPA release

Every consumer evaluates with the one Open Policy Agent (OPA) release the package pins.
`iltero_schemas.opa.OPA_RELEASE_PIN` holds the release (`version`, `release_tag`) and the SHA-256 of its binary for
each platform.

| Platform key | Release file |
| --- | --- |
| `linux-x86_64` | `opa_linux_amd64_static` |
| `linux-aarch64` | `opa_linux_arm64_static` |
| `darwin-x86_64` | `opa_darwin_amd64` |
| `darwin-aarch64` | `opa_darwin_arm64_static` |
| `windows-x86_64` | `opa_windows_amd64.exe` |

Before every run, a consumer computes the SHA-256 of the binary and compares it with the pinned digest for its
platform. It refuses to run a binary whose digest differs.

```python
import platform

from iltero_schemas.opa import OPA_RELEASE_PIN, platform_key

entry = OPA_RELEASE_PIN.binaries[platform_key(platform.system(), platform.machine())]
entry.asset, entry.sha256, OPA_RELEASE_PIN.version
```

`platform_key` raises `KeyError` for an unsupported platform.

A record states the binary each evaluation ran; a verification report's `evaluator_binary` property compares it with
this pin (see [VerificationReport](01-document-formats.md#verificationreport)). The one record vector made by hand,
`records/iac/local_run_on_placeholders.json`, names a placeholder OPA digest, so its `evaluator_binary` is `failed`. In
`records/iac/local_run_scanned_then_another_plan_applied.json` no evaluator ran, so it names no binary. Every other
record vector names the pinned binary for its platform.

## The pinned scanner releases

In a run Iltero Platform opens, the Iltero CLI runs each scanner a stage requires itself, and only the release the
package pins: Trivy 0.76.2 and Checkov 3.4.3. `iltero_schemas.scanners.SCANNER_PIN` holds them, loaded from
`src/iltero_schemas/scanners/common/PIN.json` and the files beside it. A consumer checks what it downloads against the pinned
digests, and what it runs before every run, and refuses on a mismatch. Platforms are named as for the OPA release.

Trivy is one program. For each platform the pin gives the release archive, its format (`tar.gz` or `zip`), SHA-256
digest and size, and the program inside it, with its own digest and size. The Linux programs are static, so they also
run on a musl-based Linux.

| Platform key | Release archive | Program |
| --- | --- | --- |
| `linux-x86_64` | `trivy_0.76.2_Linux-64bit.tar.gz` | `trivy` |
| `linux-aarch64` | `trivy_0.76.2_Linux-ARM64.tar.gz` | `trivy` |
| `darwin-x86_64` | `trivy_0.76.2_macOS-64bit.tar.gz` | `trivy` |
| `darwin-aarch64` | `trivy_0.76.2_macOS-ARM64.tar.gz` | `trivy` |
| `windows-x86_64` | `trivy_0.76.2_windows-64bit.zip` | `trivy.exe` |

Trivy's checksums file (`trivy_0.76.2_checksums.txt`) and its Sigstore signature bundle ship beside the pin. The pin
records the certificate identity of Trivy's release workflow at the release tag, its issuer, the release commit and the
transparency log index. A valid signature shows that the release came from Trivy's release workflow; it does not show
that the release is safe, and it does not guard against a compromise of that workflow.

Checkov is installed as Python packages. For each platform, wheel platform and Python version, the pin gives a hash lock
under `scanners/common/locks/`: a requirements file with one line per package,
`name==version --hash=sha256:<hex>  # <wheel file>`, sorted, wheels only. The pin also records the Checkov wheel and its
digest, the publisher its PyPI provenance names, which must be Checkov's (`bridgecrewio/checkov`, workflow `build.yml`,
environment `release`), and the time its packages were resolved before (`resolved_before`): each lock's wheels were
uploaded before it. Python versions are interpreter tags, `cp311` to `cp314`.

| Platform key | Wheel platform | Python versions |
| --- | --- | --- |
| `darwin-aarch64` | `macosx_11_0_arm64` | `cp311` to `cp314` |
| `darwin-x86_64` | `macosx_10_15_x86_64` | `cp311` to `cp314` |
| `linux-x86_64`, `linux-aarch64` (glibc) | `manylinux_2_17_<arch>` | `cp311` to `cp313` |
| `linux-x86_64`, `linux-aarch64` (glibc) | `manylinux_2_28_<arch>` | `cp314` |
| `linux-x86_64`, `linux-aarch64` (musl) | `musllinux_1_2_<arch>` | `cp311` to `cp314` |
| `windows-x86_64` | `win_amd64` | `cp311` to `cp314` |

Windows on ARM is not covered. Loading the pin refuses:

- a `PIN.json` that does not pin exactly the scanners a record may name, `checkov` and `trivy`;
- a checksums line that is malformed or names a file twice, and an archive digest the kept checksums file does not
  give;
- a lock whose file name does not match its release, wheel platform and Python version, whose `python_version` is not
  an interpreter tag, or whose wheel platform is not of its platform's architecture;
- a lock whose file digest is not the one the pin gives, a lock line that names no wheel, and lines out of order;
- a platform, wheel platform and Python version locked twice.

A report of a scanner the Iltero CLI ran names the digest of what ran: the program's digest for Trivy, and the lock
file's digest for Checkov. glibc and musl share a platform key, so the digest tells which lock was installed. The
digest covers neither the Python interpreter, the operating system nor the Iltero CLI itself. In a run the tool opened,
a report the Iltero CLI ran claims no more than one the pipeline ran.

```python
from iltero_schemas.scanners import SCANNER_PIN

SCANNER_PIN.version("checkov")
SCANNER_PIN.digests("checkov", "linux-x86_64", "cp312")  # the digests of the two locks, glibc and musl
SCANNER_PIN.digests("trivy", "linux-x86_64", None)
```

`version` and `digests` raise `KeyError` for a scanner the pin does not name.

A verification report's `scanner_reports` property compares what a record states with this pin (see
[VerificationReport](01-document-formats.md#verificationreport)).

Maintainers write the pin with `scripts/refresh_scanner_pin.py`, which verifies each upstream release before it records
it. CI runs `scripts/validate_scanner_pin.py` on each platform and Python version when the pin, the script, its expected
results, its sample plan or the workflow changes. The sample plan is `raw_plans/iac/plan_create.json`, the plan as
Terraform wrote it, which is what a scanner reads. The script installs both scanners from the pin, Checkov's packages
into a folder of their own, checks the installed packages with `pip check`, runs each on that plan exactly as its
[pinned run](#the-pinned-scanner-runs) says, filling the placeholders the way `filled_scanner_run` does (a test
compares the two), and compares their results with the expected ones. On Windows it requires `SYSTEMROOT` to be set.
The workflow runs on every pull
request to `main` and every push to `dev`, and skips the installs when none of those changed; its summary passes then,
so it can be a required check. Neither script is part
of the package, and neither runs in the tests.

### The pinned scanner runs

The pin also fixes how the Iltero CLI runs each scanner: one reviewed run for each input kind the scanner reads, `plan`
only. `iltero_schemas.scanners.SCANNER_RUNS` holds the runs by scanner and input kind (`ScannerRun`), loaded from
`src/iltero_schemas/scanners/iac/RUNS.json`. Changing a run is a reviewed change to that file, a change to the scanner pin,
as for `PIN.json`.

| Field | Meaning |
| --- | --- |
| `arguments` | The arguments that follow the program: Trivy's own program, or the Python interpreter for Checkov. |
| `environment` | The variables of the scanner process on every platform. With the variables below, they are its complete environment: nothing else is inherited. |
| `posix_environment` | The variables added on Linux and macOS, `PATH` among them: `/usr/bin:/bin`. |
| `windows_environment` | The variables added on Windows, `PATH` among them: `{system_root_folder}\System32`. |
| `files` | The contents of each file the Iltero CLI writes before the scanner starts, keyed by the placeholder of its path, which is a whole argument. Trivy's configuration file and ignore file are both empty. |
| `working_folder` | The folder the scanner process starts in. |

Every path the Iltero CLI chooses is a placeholder that names its role: `{input_file}`, `{working_folder}`,
`{home_folder}`, `{temporary_folder}`, `{cache_folder}`, `{config_file}`, `{ignore_file}`, `{packages_folder}` and
`{system_root_folder}`. `{name}` stands for the value given; `{name!r}` stands for its Python `repr`, for a value placed
inside Python code, such as Checkov's packages folder. In an argument, a placeholder is the whole argument or a `repr`,
so a path is never read as part of an option or of code. A value is filled once: a brace it holds is never read as a
placeholder.

The Iltero CLI starts the scanner in a new, empty working folder, with new, empty home and temporary folders and, where
the run names one, a new, empty cache folder. The input file is a copy of the plan the stage hashed, alone in its
folder. The process gets no environment variable but the run's.

The configuration digest of a run is the digest of its canonical JSON as `RUNS.json` holds it, placeholders unfilled,
so every runner gives the same digest. It covers both systems' environments, the program search path included. A
report of a scanner the Iltero CLI ran names it as `configuration_digest`. Like the program digest, it is the record's
own claim, and it covers neither the Python interpreter, the operating system nor the Iltero CLI.

| Function | Gives | Raises |
| --- | --- | --- |
| `scanner_configuration_digest(tool, input_kind)` | The run's configuration digest. | `KeyError` for a run the pin does not hold. |
| `filled_scanner_run(tool, input_kind, values, windows)` | A `FilledScannerRun`: the arguments, the environment (`windows_environment` added when `windows` is true, `posix_environment` otherwise), the files keyed by their filled paths, and the working folder, each placeholder replaced by its value in `values`. | `KeyError` for a run the pin does not hold. `ValueError` when `values` does not name exactly the placeholders the run names on that system ("the `<tool>` run over `<input_kind>` needs a value for exactly: `[...]`"), when a value is empty, starts with a dash, or holds a NUL or a line break ("`<name>` is empty, starts with a dash or holds a NUL or a line break"), or when one value is given for two placeholders ("the `<tool>` run over `<input_kind>` is given one value for two placeholders"). |
| `ScannerRun.environment_on(windows)`, `ScannerRun.placeholders(windows)` | The environment the scanner process receives, and the placeholders the run names, on Windows or on Linux and macOS. | Nothing. |
| `parse_scanner_runs(raw)` | The runs a `RUNS.json` document holds. | `ValueError`, as below. |

```python
from iltero_schemas.scanners import scanner_configuration_digest

scanner_configuration_digest("trivy", "plan")  # "sha256:..."
```

Loading the runs reads `RUNS.json` strictly (each key once, no `NaN`) and refuses:

- a document that does not hold the runs of exactly `checkov` and `trivy`, or a scanner with no run or with a key that
  is not an input kind;
- a run that does not hold exactly its six fields, or whose arguments are not a list of strings, none empty;
- an `environment`, `posix_environment`, `windows_environment` or `files` that does not map names to strings;
- an environment variable that is not in capitals, or that is named twice on one system: a name may be in both
  `posix_environment` and `windows_environment`, never beside `environment` ("names each environment variable once on
  each system, in capitals");
- a placeholder in an argument that is neither the whole argument nor a `repr` ("puts a placeholder only as a whole
  argument or a repr");
- a `files` key that is not a placeholder standing alone as a whole argument, without `!r` ("files names only
  placeholders that are whole arguments, not a repr");
- a `working_folder` that is not one placeholder, and a brace that is not part of a placeholder.

## Running the evaluation vectors

A compiled program may call only the functions in the capabilities allowlist, `iltero_schemas.opa.CAPABILITIES`
(written to a file for OPA). Its digest is `iltero_schemas.opa.CAPABILITIES_DIGEST`. Each evaluation case runs
the case's compiled program from `compiler/` over the case's input:

```bash
opa eval --format json --strict-builtin-errors \
  --capabilities capabilities.json \
  --data ILT.IAC.RESOURCE.AWS.RDS.STORAGE_ENCRYPTED.rego \
  --stdin-input \
  'data.iltero.assertions["ILT.IAC.RESOURCE.AWS.RDS.STORAGE_ENCRYPTED"].evaluate' < input.json
```

The query is always `data.iltero.assertions["<ID>"].evaluate`. OPA returns a list with exactly one result. Its
`subject`, `status`, `reason`, `observations.unknown`, `observations.when` and, where the case gives them,
`observations.predicates` must equal the expected values.

For `facts_unknown.json`, the case's assertion id replaces `evaluation.assertion.id` in the context. With
`unknown_marker`, the facts stay as the markers the context holds. With `empty_list`, `evaluations` and
`approvals` each become `[]`. A missing fact must give `unknown`, never `fail`.

Each compiled program must also pass `opa check --strict --capabilities capabilities.json`.

## Version rule

Vectors belong to the version that ships them. A consumer pins one exact version (`iltero-schemas==X.Y.Z`) and
reproduces that version's vectors. Before 1.0, a change to any computed result raises the minor version: a digest, a
canonical form, a compiled program, the OPA pin or the scanner pin (`src/iltero_schemas/scanners/`). To upgrade, a
consumer moves its pin and reproduces the vectors again.
