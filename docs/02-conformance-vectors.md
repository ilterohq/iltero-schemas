# Conformance vectors

A conformance vector is a known input with the exact output an implementation of the contract must produce. The
vectors ship inside the package, under `src/iltero_schemas/vectors/`, and are available at run time as
`iltero_schemas.vectors.VECTORS`. A consumer that reproduces every vector of the version it pins is conformant. A
consumer that fails one must fail its build.

## Vector folders

| Folder | Contents | What a consumer reproduces |
| --- | --- | --- |
| `canonical/` | `values.json` and `cases.json`: sample values with their canonical bytes and digests. `iac/plan_values.json`: sample plans, each with its IaC tool. `iac/plan_digest_cases.json`: the same plans with the version of their tool's rule, their canonical bytes and their plan digest. `assertion_set_cases.json`: inputs to the assertion-set digest, with the canonical bytes and digest of each. `change_digest_cases.json`: inputs to the change digest (`change_type`, `unit`, `environment_key`, `checked_content`), with the canonical bytes and digest of each: one unit's plan in production, the same plan outside any environment (`environment_key: null`) and in staging, a re-planned unit, another unit, and the same plan digest under another version of its digest rule; and, for `image_release`, one image in production and the same image in staging, the same checked content with another change digest. | The canonical bytes and every digest. |
| `assertions/` | Assertions written to exercise the language: truth tables, every comparison, comparisons with `null` (`VEC.OPS.NULL`), nesting and edge-case literals. | Parsing each one. |
| `compiler/` | For every shipped assertion and every vector assertion: the abstract syntax tree (`.ast.json`, which includes the `change_type`: JSON with keys sorted, two-space indentation, non-ASCII characters escaped and one final newline, the same bytes as a record's `<ID>@<version>.ast.json` file for that assertion), its source digest (`.digest`), the compiled Rego program (`.rego`) and the program's digest (`.rego.digest`). Also `COMPILER_VERSION` and `RUNTIME.digest`, the digest of the shared runtime every program embeds. | The AST, the source digest, the compiled bytes and the program digest. |
| `assertions_invalid/` | Assertions that must be refused. `expected.json` names, for each, the key and message of the first problem. Among them: a comparison whose value is missing (`missing_operand`), refused by the loader, and `null` with an ordering comparison (`null_with_ordering`). | The refusal, at the same key. |
| `contexts/` | Complete assurance contexts, each of one profile (not every profile has one): `iac/plan_resource.json`, `iac/pre_deploy_change.json`, `iac/post_deploy.json`; `iac/post_deploy_state_not_read.json`, the same post-deploy input whose state after the apply was not read; `iac/post_verify.json`, with a drift check; `image/plan_artifact.json`, the input of an image build at its `plan` stage, with the image and its build commit, a test report, a scan report, the verified source with the CI run it was verified for, and a verified attestation of that run; `iac/pre_deploy_approvals.json`, the pre-deploy input `evaluation/approvals.json` varies; and `image/post_verify.json`, the input of an image deploy at its `post_verify` stage, with the deployed image, the image the pipeline reports it deployed and one reading of the workload: a Deployment whose rollout finished, whose two live pods run the deployed image, and that compares the container of the deployed image and not its sidecar; its `change.build` is the unknown marker, since the tool opened the run. `image/pre_deploy_change.json` is the input of the same image deploy at its `pre_deploy` stage, for `ILT.IMAGE.BUILD_ACCEPTED_FOR_ENVIRONMENT`, in a run the tool opened: `change.build` and `organization_scope.environment.production` are the unknown marker, and so are the facts only Iltero Platform holds, `commit_review` among them. `iac/pre_deploy_change.json` carries a commit review whose outcome is `not_reviewed`: three commits since the review starting point, two of them not reviewed, one for `no_pull_request` and the head commit for `no_qualifying_approval`; in `iac/pre_deploy_approvals.json` the commit review is the unknown marker. `digests.json` gives each one's `input_digest`. | Validation, and each document digest. |

A folder that holds documents of both change types splits them into `iac/`, for changes made with an
infrastructure-as-code (IaC) tool, and `image/`, for container image builds and deploys: `contexts/`, `records/`,
`reports/`, `contexts_invalid/`, `records_invalid/`, `records_valid/`, `records_integrity_failed/` and
`reports_invalid/`. `events/` holds IaC events only, in `iac/`, and `canonical/` keeps its IaC plan files in `iac/`.
Each split case folder has a `cases.json` in both subfolders. A case names its document by its path from the
document folder, the folder of complete documents the case changes or evaluates (`records/`, `contexts/`,
`reports/` or `identities/`): `"vector": "image/local_run_build.json"` names `records/image/local_run_build.json`, and
`"context": "iac/pre_deploy_approvals.json"` in `evaluation/approvals.json` names
`contexts/iac/pre_deploy_approvals.json`. No two cases of one folder share a name, across both subfolders.

Each document folder (`contexts/`, `events/`, `identities/`, `records/`, `reports/`) has one `digests.json` at its
top. Each key is a document's path from that folder, such as `image/post_verify.json`, the same string a case's
`vector` or `context` uses, and the keys are sorted by Unicode code point. A listing names exactly its folder's
documents: a document not in it is not a vector, and every listed document is shipped. A consumer reads each document
folder's `digests.json` and every `cases.json` it finds, never a fixed list of subfolders, and never keys a document by
its file name alone: `contexts/iac/post_verify.json` and `contexts/image/post_verify.json` share one.

The identity vectors hold no resolved identity, because a resolved identity names a real-format cloud identifier, which
this repository does not publish. So these rules of a resource identities document have no vector: no two entries of
`resolved`, or of `removed`, name the same cloud identity; a resource is resolved or unresolved, never both; only a
resource type verified for its provider's resolver is resolved; every resolved identity belongs to the unit and names
the tool that wrote the state; an identifier names a resource of its stated type. A conformant consumer enforces them
all; the validating model `iltero_schemas.models.iac.resource_identities.ResourceIdentities` is the reference.

Every document digest is the SHA-256 of the document's RFC 8785 canonical JSON, written `sha256:<hex>`. The
`iltero_schemas.canonical` module computes it with `digest_of`, and the canonical bytes with `canonical_bytes`.
Each document vector is written as its validating model dumps it: every optional field present, `null` when it has
no value. A consumer whose writer produces that form reproduces the vector's bytes and digest.

## The pinned OPA release

Every consumer evaluates with the one Open Policy Agent (OPA) release the package pins.
`iltero_schemas.opa.OPA_RELEASE_PIN` holds the release (`version`, `release_tag`) and the SHA-256 of its binary for
each platform.

| Platform key | Release file |
| --- | --- |
| `linux-x86_64` | `opa_linux_amd64_static` |
| `linux-aarch64` | `opa_linux_arm64_static` |
| `darwin-x86_64` | `opa_darwin_amd64` |
| `darwin-aarch64` | `opa_darwin_arm64_static` |
| `windows-x86_64` | `opa_windows_amd64.exe` |

Before every run, a consumer computes the SHA-256 of the binary and compares it with the pinned digest for its
platform. It refuses to run a binary whose digest differs.

```python
import platform

from iltero_schemas.opa import OPA_RELEASE_PIN, platform_key

entry = OPA_RELEASE_PIN.binaries[platform_key(platform.system(), platform.machine())]
entry.asset, entry.sha256, OPA_RELEASE_PIN.version
```

`platform_key` raises `KeyError` for an unsupported platform.

## Running the evaluation vectors

A compiled program may call only the functions in the capabilities allowlist, `iltero_schemas.opa.CAPABILITIES`
(written to a file for OPA). Its digest is `iltero_schemas.opa.CAPABILITIES_DIGEST`. Each evaluation case runs
the case's compiled program from `compiler/` over the case's input:

```bash
opa eval --format json --strict-builtin-errors \
  --capabilities capabilities.json \
  --data ILT.AWS.RDS.STORAGE_ENCRYPTED.rego \
  --stdin-input \
  'data.iltero.assertions["ILT.AWS.RDS.STORAGE_ENCRYPTED"].evaluate' < input.json
```

The query is always `data.iltero.assertions["<ID>"].evaluate`. OPA returns a list with exactly one result. Its
`subject`, `status`, `reason`, `observations.unknown`, `observations.when` and, where the case gives them,
`observations.predicates` must equal the expected values.

For `facts_unknown.json`, the case's assertion id replaces `evaluation.assertion.id` in the context. With
`unknown_marker`, the facts stay as the markers the context holds. With `empty_list`, each of `evaluations`,
`approvals` and `exceptions` becomes `[]`. A missing fact must give `unknown`, never `fail`.

Each compiled program must also pass `opa check --strict --capabilities capabilities.json`.

## Version rule

Vectors belong to the version that ships them. A consumer pins one exact version (`iltero-schemas==X.Y.Z`) and
reproduces that version's vectors. Before 1.0, a change to any computed result raises the minor version: a digest, a
canonical form, a compiled program or the OPA pin. To upgrade, a consumer moves its pin and reproduces the vectors
again.
