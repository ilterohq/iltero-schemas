# Conformance vectors

A **vector** is a file with a known input and the exact output the code must
produce for it. Vectors let two programs prove they agree on the contract.

The vectors ship inside the package. Anyone who uses it can run them against
the version they installed. That includes the Iltero CLI, Iltero Compass and
any third party. If every vector is reproduced, both sides agree on the
contract. If one is not, that build must fail.

## What the vectors cover

Some vectors are written by hand. Others are generated by a script from the
code, and the script also checks that they are still current.

| Folder | What it holds | How it is made |
| --- | --- | --- |
| `canonical/` | `values.json` holds sample values, and `cases.json` their canonical bytes and fingerprints. `plan_values.json` holds sample plans, and `plan_digest_cases.json` their canonical bytes and plan digests. `assertion_set_cases.json` and `change_digest_cases.json` hold inputs to the assertion-set and change digests, with the canonical bytes and digest of each. One assertion-set case, named `starter_set`, is the set of the ten assertions this package ships. A test checks that it still matches them | Inputs by hand. Bytes and digests by `scripts/refresh_vectors.py` |
| `assertions/` | Small assertions written only to exercise the language, such as truth tables, each comparison and nesting | By hand |
| `compiler/` | For every shipped and vector assertion, four files. They are the AST (abstract syntax tree) as JSON (`.ast.json`), its fingerprint (`.digest`), the compiled program (`.rego`) and its fingerprint (`.rego.digest`). The folder also holds `COMPILER_VERSION`, and `RUNTIME.digest`, the fingerprint of the shared runtime | `scripts/refresh_vectors.py` |
| `invalid/` | Documents that must be rejected. `expected.json` names the key and the message of the first problem in each | By hand |
| `evaluation/` | `cases.json` gives an assertion, an input, and what OPA must return: the status, the reason, the unknown value and, for some, the observations. `facts_unknown.json` runs the approval and exception assertions over `contexts/pre_deploy_change.json`. They give `unknown` with the facts markers, and `fail` with empty lists | By hand |
| `contexts/` | One complete assurance context per profile, and `digests.json` with the `input_digest` of each. `plan_resource.json` is a production RDS change at the `plan` stage. `pre_deploy_change.json` is the same change at `pre_deploy`, with all its facts set to unknown markers. `post_deploy.json` is a context at the `post_deploy` stage. The tests also check that the three RDS assertions (encryption, public access and backup retention) pass on `plan_resource.json` | Contexts by hand. `digests.json` by `scripts/refresh_vectors.py` |
| `events/` | A complete assurance event, `plan_pass.json`, which is the verdict for the context above, and `digests.json` | The event by hand. `digests.json` by `scripts/refresh_vectors.py` |
| `reports/` | A complete verification report, `verification_report.json`, and `digests.json` (see [verification reports](../usage/14-verification-reports.md)) | The report by hand. `digests.json` by `scripts/refresh_vectors.py` |
| `wire/` | One document per run message, each read as the model its name gives, and `digests.json`. The messages are `run_open_request.json`, `run_open_response.json`, `token_refresh_request.json`, `token_refresh_response.json`, `run_close_response.json`, `assurance_facts.json`, `assurance_event_batch.json` and `submission_outcome.json` | Documents by hand. `digests.json` by `scripts/refresh_vectors.py` |
| `wire_invalid/` | `cases.json` lists wire documents that must be refused. Each case names a `wire/` document, the values to change (`set`) and to remove (`remove`) by JSON Pointer, and the message of the problem | By hand |
| `opa/` | `not_allowed.txt` lists every built-in function of the pinned OPA release that the allowlist leaves out | `scripts/refresh_capabilities.py` |

## Running the tests that need OPA

Some tests need the pinned OPA (Open Policy Agent) binary:

- The evaluation cases.
- The checks that OPA accepts each compiled program (`opa check --strict
  --capabilities`, `opa fmt` and `opa build`).
- The signed-bundle tests. In them, OPA verifies a bundle this package
  built and refuses a tampered one.

Point `ILTERO_OPA_PATH` at the binary, or put `opa` on `PATH`. The tests hash
the binary first. A different release fails the tests. No binary at all
skips them. CI sets `ILTERO_OPA_REQUIRED=1`, so there a missing binary fails
instead of skipping.

To get the binary, run `python scripts/fetch_opa.py DIR`. It downloads the
release for your machine and checks the download against the
[OPA pin](../usage/01-opa-pin.md). Only then does it keep the file. CI does the same.

The bundle tests sign with a throwaway key made for each run. They use the
`cryptography` development dependency. There is no signed-bundle vector,
because an ES256 signature differs every time it is made.

## Changing the parser, the compiler or the runtime

1. Make the change, with its tests.
2. If any byte of a compiled program changes, bump the compiler's version.
   If the JSON form of the parsed assertion (the AST) changes, bump the AST
   version, which is 2 today. Both are breaking changes to the contract (see
   [versioning](02-versioning.md)).
3. Run `pdm run python scripts/refresh_vectors.py`. Read the diff of the
   vectors as carefully as the code, because every user of the package will
   reproduce it.

The script refuses to run when the shared runtime changed but the
compiler's version did not. Otherwise every recorded program fingerprint
would change while the version that explains the change stayed the same.
The test suite runs the script with `--check`, which fails when the vectors
and the code disagree.

## Changing the list of allowed OPA functions

The capabilities file names the functions a compiled program may call. The
list of names is the decision. The rest of the file only describes those
functions to OPA.

When the OPA pin moves, run `python scripts/refresh_capabilities.py <opa>`
with the newly pinned binary. The script does four things:

1. It checks the binary's fingerprint.
2. It rewrites the function declarations from that binary and keeps the same
   names.
3. It stops if one of the names has disappeared.
4. It rewrites the list of functions the allowlist leaves out. So every
   function the new release added shows up in the diff, and someone must
   accept or reject it on purpose.

The test suite runs the script with `--check`. It fails when either file
does not match the pinned binary.

| What | Where |
| --- | --- |
| The capabilities file | `src/iltero_schemas/opa/capabilities.json` |
| The functions it leaves out | `src/iltero_schemas/vectors/opa/not_allowed.txt` |
